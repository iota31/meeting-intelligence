# Plan-derived acceptance suite

## Context

To provide credible contract evidence, add a **retroactive, black-box acceptance suite** derived from `IMPLEMENTATION_PLAN.md`, rather than adapting tests to internal implementation details. The result must be reported honestly as post-implementation contract/integration coverage - not historical red-green-refactor TDD.

The suite will run through the local HTTP API and the rendered browser UI, using the real local stack (Ollama, Chroma, SQLite, and WhisperX where applicable). It will not mock the AI paths or import application internals to make results easier to satisfy.

## Constraints

- The test author reads the implementation plan, test fixtures it creates, API responses, and browser UI - not backend or frontend implementation source or pre-existing verifier scripts.
- Test expectations originate only from plan contracts, DoD requirements, and observable UI behavior. Once written, an assertion is not relaxed to accommodate an implementation failure; fixes happen in production code instead.
- Preserve existing data: tests create uniquely titled synthetic meetings and do not delete or overwrite user meetings.
- Keep audio in a separately marked integration group because it requires local WhisperX, ffmpeg/espeak, models, and gated diarization access.
- Use real local services; no fake Ollama, WhisperX, vector-store, or HTTP responses.

## Implementation

### 1. Add test tooling and test configuration

**Files to add/modify**
- `requirements-dev.txt`  -  `pytest` only; keep production requirements unchanged.
- `pytest.ini`  -  register `audio`, `llm`, `limits`, and `smoke` markers; keep default collection limited to deterministic/standard API tests.
- `package.json` at repo root (or a small `tests/package.json` if the project has no root package manifest)  -  add Playwright as a test-only dependency and stable commands for the browser smoke test.
- `.gitignore`  -  ignore Playwright reports, downloaded browser artifacts, and screenshots generated by test failures.
- `README.md`  -  add concise commands/prerequisites for the new contract suite and browser smoke test; call them retroactive plan-derived tests, not historical TDD.

Use `pytest` + existing `httpx` as a live HTTP client. Use Playwright for the primary user-facing regression suite; avoid unit/component/pixel test frameworks, mocks, snapshots, and test abstractions.

### 2. Create independent HTTP contract/integration tests

**Files to add**
- `tests/contract/conftest.py`
- `tests/contract/test_transcript_ingest.py`
- `tests/contract/test_audio_ingest.py`
- `tests/contract/test_extraction_and_items.py`
- `tests/contract/test_grounded_chat.py`
- `tests/contract/test_safety_and_errors.py`
- `tests/fixtures/plan_contract_meeting.txt`
- `tests/fixtures/plan_contract_meeting_b.txt`

The fixture transcript must contain explicit, unambiguous evidence for a decision, an action owner/due date, an unsupported fact, and one prompt-injection-like line. Do not reuse existing implementation verification fixtures or their expected outputs.

All API tests target `TEST_API_BASE_URL` (default `http://127.0.0.1:8000`) and use a generated title prefix. The suite validates real HTTP responses only.

**Hard plan-derived assertions**

- `GET /health` succeeds before all dependent tests.
- Transcript upload returns `{meeting_id, turn_count, status: "ok"}`.
- Meeting detail returns the documented meeting, ordered `TranscriptTurn[]`, and items array.
- Every transcript turn has exactly the canonical fields/types: `turn_id`, `speaker`, integer `start_ms`, integer `end_ms`, `text`; IDs begin at `turn_000`, times are ordered and non-negative, and `end_ms >= start_ms`.
- Malformed transcript and a missing resource return a 4xx response with the planned `{error: {code, message}}` shape.
- Audio upload (marker `audio`) returns the same canonical turn field semantics and `source_type="audio"`. Generate a tiny WAV with espeak/ffmpeg at test time so no large/binary fixture enters the repository.
- Extraction returns at least one decision and action item for the explicit fixture, each with a non-empty citation. Each citation must resolve **exactly** to a stored turn in the same meeting (turn id, speaker, start, end all match).
- `PATCH /items/{id}` changes an item to confirmed and dismissed; GET detail reflects the update; re-extraction cannot regress either non-pending status.
- An answerable question returns non-empty answer text and one or more citations that resolve only to stored turns for that meeting.
- A question supported only by Meeting B asked against Meeting A must explicitly refuse and never cite a Meeting B turn/speaker/time.
- Unsupported and injection-style questions explicitly refuse and return no citations.
- Empty/invalid chat input is rejected through the documented error response.
- A clearly oversized uploaded audio payload (marker `limits`) is rejected before AI processing. Do not assert an undocumented exact byte threshold.

Do not assert LLM prose verbatim, extraction order/count, response latency, retrieval scores, diarization speaker identity, or visual styling. Those are not fixed by the plan.

### 3. Add Playwright user-workflow tests for the revised UI

**Files to add**
- `tests/e2e/meeting-workflows.spec.ts`
- `playwright.config.ts`

Before defining selectors, the test author must inspect the **running UI** through the browser, then write tests only against its actual user-facing, accessible controls and visible outcomes. It must not use selectors, text, layout assumptions, or component names from any earlier UI revision.

The test drives the revised UI against the local backend and Vite app. Split it into three focused Playwright workflows:

1. **Upload and transcript workflow**: load the dashboard; verify the revised upload control and meeting navigation; upload `tests/fixtures/plan_contract_meeting.txt`; open the created meeting; verify visible transcript evidence includes speaker, timestamp, and text.
2. **Extraction and item-state workflow**: trigger extraction through the revised UI; verify decision/action item cards and their visible citations; confirm an item; reload or re-open; verify the UI still shows confirmed state. If the revised UI presents Dismiss, independently verify that transition too.
3. **Grounded chat workflow**: ask the fixture’s grounded question; verify an answer plus at least one visible citation; activate a citation and verify its matching transcript evidence becomes visible, focused, or highlighted; ask the unsupported question and verify explicit refusal with zero visible citations.

Browser assertions validate user functionality and accessibility semantics, not exact answer wording, implementation/component hierarchy, colors, layout geometry, exact extraction counts, or text styling. Capture screenshots/traces only for failed tests.

### 4. Execute a transparent retroactive TDD loop

1. Commit the plan-derived test definitions first; keep their assertions fixed.
2. Run the deterministic API contract group against the already running local backend and record its initial pass/fail baseline.
3. Run the `llm`, `audio`, and `limits` groups separately with required local dependencies active; record failures independently rather than hiding them with retries.
4. Run the three Playwright workflows against the active revised Vite UI. Capture a failure screenshot/trace only on failure.
5. If a test reveals a deviation, inspect the relevant production code **after** the failing test is recorded, apply the smallest production fix, and rerun the exact failed test followed by the full suite. Never edit the contract to make an implementation pass unless the plan itself is clarified by the user.
6. Publish a short matrix in README with command, category, local prerequisites, result, and known environment warnings.

## Commands and verification

Start local dependencies first:

```bash
ollama serve
.venv/bin/uvicorn backend.main:app --host 127.0.0.1 --port 8000
npm --prefix frontend run dev -- --host 127.0.0.1 --port 5173
```

Run groups in this order:

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest tests/contract -m "not audio and not limits" -q
.venv/bin/python -m pytest tests/contract -m llm -q
.venv/bin/python -m pytest tests/contract -m audio -q
.venv/bin/python -m pytest tests/contract -m limits -q
npm run test:e2e
```

Completion criteria:

- Every hard plan-derived API assertion passes against real local services.
- Audio contract passes when the documented WhisperX/HF prerequisites are present; otherwise it remains a visible skipped/infrastructure-blocked result, never a false pass.
- All Playwright user-workflow tests pass against the revised UI.
- Any failure stays documented and is corrected in product code without weakening its original plan-derived assertion.
- README clearly distinguishes this suite from historical TDD and describes it as retroactive acceptance coverage.
